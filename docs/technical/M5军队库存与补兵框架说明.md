# M5 军队库存与补兵框架说明

## 1. 本批范围

M5-02 建立势力统一军队库存、补兵/训练事务和远征真实伤亡扣除。正式主城 UI 按玩家决定延后到 M5-06，本批只交付可由后续 UI 调用、可保存和可回归的领域接口。

Vertical Slice 只包含：

- `infantry`：步兵
- `archer`：弓兵
- `cavalry`：骑兵

军队不会成为独立场上单位，也不建立武将私人库存。

## 2. CampaignState 增量

`army_inventory` 固定保存三种兵的非负整数数量。旧 V1 存档中的空对象会在载入时补齐三项零值；未知兵种、负数、小数或非数值库存会被拒绝。

补兵事务另外保存：

- `applied_army_action_ids`：已提交的稳定操作 ID，防止重复点击/恢复导致二次扣费和加兵。
- `army_history`：兵种、批次数、实际增加数量及主/特殊资源消耗的审计记录。

## 3. 原型训练配方

`data/config/prototype_army_economy.json` 是唯一的训练参数来源，必须保留 `balance_status=prototype_temporary`。当前批次数量与价格只用于验证框架，不视为最终平衡：

- 每种兵都必须消耗兵员，避免兵源无成本变成实际士兵。
- 银钱、粮草和兵员从四主资源扣除。
- 骑兵额外消耗 `resource.warhorse`，证明特殊资源门槛能够工作。
- 军学不允许作为军队训练成本，继续留给 M5-03 公共卡研究/升级。

配方验证、报价和实际提交分离。UI 以后可以先报价再确认，但最终提交仍会重新检查全部库存并在深拷贝状态上一次完成。

## 4. 补兵事务

`CampaignController.replenish_troops()` 接收 `action_id`、`army_type`、`batches`：

1. 要求合法 CampaignState 与已验证经济配置。
2. 计算整批产出、主资源成本和特殊资源成本。
3. 任一资源不足则不修改任何资源或库存。
4. 全部满足后一次扣费、增加对应军队库存、登记幂等 ID 与流水。
5. 同一 `action_id` 再次提交返回成功重复态，但不再次扣费或加兵。

这里“补兵”和“训练兵种”共用同一长期库存转换规则：玩家选择要补充的兵种，按该兵种配方把兵源和训练资源转换为实际军队。是否在正式 UI 中根据伤亡缺口使用不同文案，留给 M5-06 的交互设计。

## 5. 远征伤亡

M4 的新结算 DTO 增加：

- `initial_troops`：本次远征开始时的实际兵力。
- `army_composition`：开战时锁定的步/弓/骑构成。

Campaign 以 `initial_troops - remaining_troops` 得到总伤亡，再按锁定构成分摊。分类取整使用确定性的最大余数法，保证：

- 三类伤亡之和严格等于总伤亡。
- 相同输入始终得到相同结果。
- 胜利、撤退和失败都承担已经发生的真实损失。
- 奖励入库、伤亡扣除、结算流水和幂等登记属于同一事务；库存不足时整笔回滚。

旧结算 DTO 没有初始兵力/构成时仍可读取，但会保存 `army_losses_applied=false`，不凭空猜测分类损失。该兼容债进入 M5-07 的迁移与恢复测试。

## 6. 自动化证据

`tests/run_m5_army_tests.gd` 覆盖三兵种库存、旧 V1 增量兼容、原型配置契约、配方报价、主/特殊资源扣除、幂等、资源不足回滚、伤亡取整、成功/撤退结算扣损和存档往返，共67项断言。

M4 结算契约新增2项出征快照断言后为70通过、0失败。M5-02 完成后的14组串行回归为1081通过、0失败；额外错误扫描未发现 `SCRIPT ERROR`、`Parse Error`、`Invalid call`、`TEST FAIL` 或非已知 macOS CA 噪声的 `ERROR:`。
